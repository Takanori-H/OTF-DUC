## One-sentence Summary

This project extends MTSA with OTF-DUC, an On-the-Fly Dynamic Update Controller Synthesis method that avoids explicitly constructing the full traditional update environment `E_u` and instead searches only the update bridge from an old controller to a new controller.

## Research Context

MTSA supports modelling, analysis, and synthesis of concurrent software systems using FSP/LTS/MTS and controller synthesis algorithms.

The research problem is Dynamic Update Controller Synthesis (DUCS): given an old controller, a new controller, old/new environments, safety properties, transition requirements, and an environment mapping, synthesize an update controller that can move the running system from the old specification to the new one without stopping.

Traditional DUCS constructs an update environment `E_u` and then solves the control problem.  The bottleneck is that `E_u` encodes the old controller, mapping environment, safety monitors, transition requirements, and update-event interleavings.  This can explode in size before synthesis even starts.

OTF-DUC keeps the DUCS semantics but replaces full `E_u` construction with DCS-style On-the-Fly exploration.  The key framing for the paper is: OTF-DUC is not changing the correctness goal of DUCS; it is changing how much of the update game has to be materialized.

## Core Update Events

The implementation uses these update events:

- `hotSwapIn`: starts the update phase and hands control from the old controller to the update controller.
- `stopOldSpec`: declares that the old safety specification no longer needs to be enforced.
- `reconfigure`: moves the system through the mapping environment from old-environment state toward new-environment state.
- `startNewSpec`: starts enforcing the new safety specification.
- `hotSwapOut`: OTF-DUC-specific completion event; allowed only when the current mapping/new-safety state can safely connect to the new controller.

In the implementation constants, `UpdateConstants.BEGIN_UPDATE = "hotSwapIn"` and `UpdateConstants.FINISH_UPDATE = "hotSwapOut"`.  The Java constant name `FINISH_UPDATE` remains for historical compatibility, but design notes and paper text should use the event name `hotSwapOut`.

`hotSwapOut` is intentionally distinct from the GR(1) guarantees used by traditional DUCS.  It is an OTF handoff condition to connect the update controller to the new controller.

## OTF-DUC Design

OTF-DUC constructs a DCS box list instead of a full update environment.  The box list is built in `UpdatingControllerSynthesizer.generateDUC`.

Current box-list structure:

| Segment | Role |
|---|---|
| index 0 | Marking LTS for update progress |
| index 1 | Old Controller with actions renamed using `_old` |
| mapping range | Mapping Environment components |
| old safety range | Old Safety properties |
| new safety range | Original New Safety properties |
| transition requirement range | Transition Requirements |
| synthesis range | Fluent-derived synthesis machines / monitors |

The new controller is deliberately excluded from the box list.  Instead, `StateMapper` precomputes a mapping from `(New Environment state, New Safety state)` signatures to new-controller states.  During exploration, `hotSwapOut` is enabled only if the current mapping environment can be translated to a new-environment state and the resulting new-environment/new-safety signature exists in the new controller.

## Marking LTS

The OTF Marking LTS is generated by `createOTFMarkingLTS` in `UpdatingControllerSynthesizer`.

The implementation uses 10 states:

| State | Meaning |
|---:|---|
| 0 | Before `hotSwapIn`; old controller still runs |
| 1 | After `hotSwapIn`; none of the three main update events completed |
| 2 | `stopOldSpec` completed |
| 3 | `reconfigure` completed |
| 4 | `startNewSpec` completed |
| 5 | `stopOldSpec` and `reconfigure` completed |
| 6 | `stopOldSpec` and `startNewSpec` completed |
| 7 | `reconfigure` and `startNewSpec` completed |
| 8 | all of `stopOldSpec`, `reconfigure`, `startNewSpec` completed |
| 9 | `hotSwapOut` completed; OTF goal state |

State 9 is the only marked goal state.  The bit meanings used by analysis scripts are `1=stopOldSpec`, `2=reconfigure`, and `4=startNewSpec`.

## Fine-grained Update Events

The `.lts` keyword `fine_grained` selects fine-grained update events.  With `on_the_fly`, it selects fine-grained OTF-DUC.  Without `on_the_fly`, it selects fine-grained Traditional DUC.  Without this flag, both modes keep the legacy bulk update events.

Fine-grained mode replaces the three bulk update events with generated per-component progress actions:

- `stopOldSpec_<safety>` for each old safety property;
- `startNewSpec_<safety>` for each new safety property;
- one `reconfigure_*` action per generated mapping component.

Relation rules may write either `reconfigure_*` explicitly or legacy `reconfigure`.  Legacy `reconfigure` is normalized internally to `reconfigure_<mapping component name>`.  Each mapping component must use only one reconfigure action.

The DCS box list still has one progress component at index 0.  It is a small synthetic slot whose concrete progress IDs are allocated by `ProgressRegistry` from BigInteger completion masks, so large models are not limited to 63 fine-grained update actions and do not need one LTS per flag.  `hotSwapOut` remains the handoff action and is available only after every fine-grained progress action is complete and the New Controller stitching guard succeeds.

Traditional fine-grained DUC keeps the traditional explicit `E_u` construction.  The fine-grained `E_u` has per-safety `stopOldSpec_*` and `startNewSpec_*` self-loops in update states, per-mapping `reconfigure_*` transitions from the generated mapping environment, DontDoTwice constraints for all fine-grained progress actions, and GR guarantees for all fine-grained progress actions.  It does not add OTF-only completion actions such as `hotSwapOut`.

## Active / Trace / Enforce Semantics

OTF-DUC controls each component with three conceptual flags:

- Active: the component can block an action if the action is in its alphabet but not enabled in its current state.
- Trace: the component updates its internal state when an observed action occurs.
- Enforce: reaching an error/sink state is treated as a fatal violation.

Before `hotSwapIn`, the old controller is active and its actions are renamed with `_old`.  The environment, safety, and fluent machines trace the corresponding unrenamed action where appropriate.

After `hotSwapIn`, the old controller is disconnected from the update path.  The mapping environment becomes the main active environment.  Old Safety is enforced until `stopOldSpec`; New Safety is enforced only after `startNewSpec`.

Trace-off components are normalized to avoid treating irrelevant component-state differences as distinct search states.

## Delayed New Safety Activation

New Safety is not enforced from the beginning of the update.  Synthesis machines derived from fluents run in the background as tracers.  When `startNewSpec` fires, `DirectedControllerSynthesisDUC` uses `safetyStateLookupMap` to jump the original New Safety component to the state implied by the current fluent/monitor state.

This is crucial: it lets the update path delay the point at which the new safety specification becomes active, while still enforcing the correct New Safety state once it starts.

## hotSwapOut Guard and Stitching

`hotSwapOut` is not always available in Marking state 8.

The hotSwapOut guard implementation in `DirectedControllerSynthesisDUC` requires:

- the current Mapping Environment state can be translated to a New Environment state;
- the translated New Environment state plus current New Safety state has a corresponding safe state in the New Controller.

After the DCS search succeeds, `buildDirectorDUC` builds the output update controller and connects `hotSwapOut` edges to the corresponding New Controller state.  This is the exit stitching step.

The output-building logic also has entry-side handling for old-controller-like pre-update states, including action-name restoration and controllability restoration.

Marking state 8 should be read carefully. At m8, the update protocol body has completed and the new safety is active; the remaining question is whether the update bridge can hand off to the pre-synthesized New Controller through `hotSwapOut`. The implementation supports two interpretations:

- default mode: m8 SCCs may be accepted under the existing fairness fixed point, so completion is a fair-completion property;
- `-Dotfduc.fairness=false` or `-Dotfduc.disableFairness=true`: m8 fairness promotion is disabled, so completion is treated as ordinary all-traces reachability. This mode is stricter and is the one to use when checking `hotSwapIn -> <> hotSwapOut` without fairness assumptions.

## Main Implementation Map

- `maven-root/mtsa/src/main/java/ltsa/updatingControllers/synthesis/UpdatingControllerSynthesizer.java`

  - selects legacy vs fine-grained Traditional DUC environment and safety synthesis paths;
  - builds OTF box list;
  - creates Marking LTS;
  - builds New Controller connection map;
  - converts New Safety/Fluent maps to box-list indices;
  - invokes `DirectedControllerSynthesisDUC`.

- `maven-root/mtsa/src/main/java/MTSTools/ac/ic/doc/mtstools/model/operations/DCS/nonblocking/DirectedControllerSynthesisDUC.java`
  - OTF-DUC search engine;
  - expands DUC compostates;
  - handles Active/Trace/Enforce behavior;
  - handles `startNewSpec` safety synchronization;
  - checks `hotSwapOut` guards;
  - handles fairness/loop reasoning and output construction;
  - records detailed evaluation metrics.

- `maven-root/mtsa/src/main/java/MTSTools/ac/ic/doc/mtstools/model/operations/DCS/nonblocking/DirectedControllerSynthesisFineGrainedDUC.java`
  - fine-grained OTF-DUC entry class;
  - owns the fine-grained protocol semantics for Active/Trace/Enforce, progress-slot transitions, update-action priority, and per-safety New Safety synchronization;
  - reuses the common search/output machinery from `DirectedControllerSynthesisDUC` through protected hooks.

- `maven-root/mtsa/src/main/java/MTSTools/ac/ic/doc/mtstools/model/operations/DCS/nonblocking/ProgressRegistry.java`
  - maps fine-grained completion masks to synthetic progress state IDs.

- `maven-root/mtsa/src/main/java/ltsa/updatingControllers/structures/UpdateProtocolSpec.java`
  - builds and classifies generated stop/reconfigure/start progress actions.

- `maven-root/mtsa/src/main/java/ltsa/updatingControllers/synthesis/FineGrainedUpdatingEnvironmentGenerator.java`
  - Traditional DUC fine-grained `E_u` generator.

- `maven-root/mtsa/src/main/java/ltsa/updatingControllers/synthesis/FineGrainedUpdatingControllersUtils.java`
  - Traditional DUC fine-grained GR and safety goal generation helpers.

- `maven-root/mtsa/src/main/java/ltsa/updatingControllers/synthesis/FineGrainedUpdatingControllerSafetySynthesizer.java`
  - Traditional DUC fine-grained safety pruning entry point;
  - delegates shared logic while passing all fine-grained progress actions to DontDoTwice.

- `maven-root/mtsa/src/main/java/MTSTools/ac/ic/doc/mtstools/model/operations/DCS/nonblocking/DUCExplorationHeuristic.java`
  - priority ordering for OTF-DUC exploration;
  - prioritizes deeper Marking progress first, then newer states (LIFO), then recommendation scores;
  - recommendation scores strongly prioritize update actions, with uncontrollable actions used before ordinary controllable actions only when scores are tied.

- `maven-root/mtsa/src/main/java/ltsa/updatingControllers/synthesis/StateMapper.java`
  - traverses the New Controller and component states;
  - builds signatures mapping New Environment/New Safety states to New Controller states.

- `maven-root/mtsa/src/main/java/ltsa/updatingControllers/synthesis/UpdatePhaseEvaluator.java`
  - analyzes update phases, update-event transitions, completion distance, phase flow, progress-free cycles, and enabled update events.

- `maven-root/mtsa/src/main/java/ltsa/updatingControllers/UpdatingControllerEvaluationRecorder.java`
  - central recorder for timing, memory, state-space, phase, output, and CSV metrics.

- `maven-root/mtsa/src/main/java/ltsa/updatingControllers/DUCHeartbeat.java`
  - optional heartbeat logger controlled by Java system properties such as `duc.heartbeat`.
